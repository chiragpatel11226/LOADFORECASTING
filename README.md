# GridWatch -- Power Demand Forecasting Dashboard

An end-to-end machine learning project: it cleans nine years of hourly
Indian power-grid demand data, trains a regression model to forecast
demand, and serves the results through an interactive Flask + Chart.js
dashboard.

**Live features:**
- Cleans and parses a messy real-world spreadsheet export into a proper time series
- Engineers calendar-based features (cyclical hour/month/day encodings, weekend flag, long-term trend)
- Trains and compares two regression models with honest, leakage-free time-series validation
- Serves six interactive charts and a live "predict demand for any date/hour" tool

---

## 1. The dataset

`data/Yearly_Demand_Profile.xlsx` is an hourly electricity demand series
published by [NITI Aayog's India Climate & Energy Dashboard](https://iced.niti.gov.in):

- **8,760 hours of 2017** (a complete calendar year)
- **2,160 hours of Jan-Mar 2026** (the most recent quarter available)
- One column: `Hourly Demand Met (in MW)` -- the actual load the grid served that hour

Two things make this dataset interesting (and slightly tricky) to model:

1. **The date column is not a real date.** It's a string like `"01-Jan
   12am"`, split across a separate `Year` column, with 12-hour AM/PM hour
   labels instead of 24-hour time. This has to be parsed by hand.
2. **The file has footer rows.** After the last data row, NITI Aayog
   appends a copyright notice, a source URL, and a disclaimer as extra
   spreadsheet rows with text in the `Year` column instead of a number.
   These have to be filtered out before doing any date math on them, or
   the entire pipeline crashes.
3. **There's a large gap in real-world conditions between the two years.**
   Average demand in the 2026 slice is roughly 40% higher than in 2017.
   That's not noise -- it reflects genuine multi-year growth in grid
   demand -- but it has real consequences for modeling (see Section 3).

├── render.yaml                        # one-click deploy config for Render

**Why this separation?** `preprocess.py` contains the *only* place where
raw data becomes model features. Both `train_model.py` (offline training)
and `app.py` (live prediction) import from it, so the feature formulas can
never drift out of sync between training and serving -- a very common
source of silent bugs in real ML systems ("training/serving skew").

## 3. Feature engineering (`src/preprocess.py`)

| Feature | What it is | Why it's there |
|---|---|---|
| `hour_sin`, `hour_cos` | Hour of day (0-23), sine/cosine encoded | Hour 23 and hour 0 are one hour apart in reality but "23 apart" as raw integers. Cyclical encoding wraps the value onto a circle so the model sees midnight and 11pm as neighbours. |
| `month_sin`, `month_cos` | Month (1-12), sine/cosine encoded | Same idea, for the yearly seasonal cycle (December and January are adjacent). |
| `dow_sin`, `dow_cos` | Day of week (0-6), sine/cosine encoded | Same idea, for the weekly cycle. |
| `is_weekend` | 0/1 flag | Weekday vs weekend load differs (commercial/industrial demand drops). |
| `day_of_year` | 1-365 | Captures finer-grained seasonal drift than month alone (e.g. early vs late summer). |
| `trend_days` | Days since the first timestamp in the dataset | See below -- this is the single most important feature. |

### Why `trend_days` matters (be ready to explain this)

An early version of this model used *only* seasonal features (hour, month,
day of week) and it performed terribly on the 2026 test data (R² was
**negative** -- worse than just predicting the average). The reason:
seasonal features repeat identically every year, so a model trained only
on 2017 has no way to know that demand in 2026 runs ~40% higher across the
board. It would confidently predict 2017-level demand for every date,
no matter the year.

Adding `trend_days` (a plain numeric day-count) gives the model a way to
represent long-term growth explicitly, on top of the seasonal shape. This
took R² from negative to **0.92** on the same test set. It's a good story
for an interview because it shows you don't just fit a model and read the
score -- you diagnose *why* a model fails and fix the actual cause.

**A deliberate trade-off:** I did *not* add lag features (e.g. "demand 24
hours ago", "demand 1 week ago"), which are common in demand forecasting
and usually improve short-horizon accuracy further. I left them out
because the dashboard lets a user ask hypothetical questions like "what
would demand look like on a Tuesday in July at 3pm?" -- for a date that
isn't adjacent to any known history, there's no real "24 hours ago" value
to feed in. Calendar-only features trade a bit of accuracy for the
ability to answer open-ended what-if questions. If this were a
production next-hour forecasting system instead of an exploratory
dashboard, I would add lag/rolling features and accept that the model
could only forecast a short horizon ahead of the latest known reading.

## 4. Model training and evaluation (`src/train_model.py`)

### Train/test split: why not just shuffle and split 80/20?

A random shuffle-split is the **wrong** choice for time series. If you
shuffle hourly rows randomly, the model can end up training on 2pm and
4pm of a given day and being tested on 3pm of that same day -- it "leaks"
information from the neighbourhood of the test point and makes accuracy
look artificially good.

Instead, this project uses a **chronological split**: sort everything by
timestamp, train on all but the most recent 30 days, and test only on
that final unseen month. Every test point comes strictly after every
training point -- exactly the situation a real deployment faces ("I have
data up to today, how well can I predict next month?").

### Models compared

| Model | Why it's here |
|---|---|
| **Linear Regression** (baseline) | Fast, transparent, a sanity floor. If a fancier model can't clearly beat this, the added complexity isn't worth it. |
| **Random Forest Regressor** (chosen model) | Demand depends on *interactions* between features -- "weekday AND evening AND summer" behaves differently than any one of those alone. A Random Forest captures these interactions automatically (an ensemble of decision trees, each trained on a bootstrapped sample of the data and a random subset of features at each split, with predictions averaged across trees), needs no feature scaling, is robust to outliers, and gives feature importances for free. |

### Results on the held-out test month

| Model | MAE (MW) | RMSE (MW) | MAPE | R² |
|---|---|---|---|---|
| Linear Regression | ~20,400 | ~25,100 | ~11.9% | 0.23 |
| **Random Forest** | **~6,100** | **~8,100** | **~3.3%** | **0.92** |

*(Exact numbers are written to `models/metrics.json` each time you retrain --
they may shift slightly with hyperparameter tweaks.)*

### What each metric means (interview cheat-sheet)

- **MAE (Mean Absolute Error):** average absolute difference between
  predicted and actual demand, in MW. Easy to explain to a non-technical
  audience: "on average, the model is off by about 6,100 MW."
- **RMSE (Root Mean Squared Error):** like MAE, but squares errors before
  averaging, so large misses are penalized more heavily. RMSE ≥ MAE
  always; the gap between them tells you whether errors are consistent
  or occasionally very large.
- **MAPE (Mean Absolute Percentage Error):** MAE expressed as a
  percentage of the actual value. Useful because it's scale-free -- "3.3%
  error" means something even to someone who doesn't know if 6,100 MW is
  a lot.
- **R² (coefficient of determination):** the fraction of variance in
  actual demand explained by the model, relative to always guessing the
  mean. R²=1 is a perfect fit, R²=0 is no better than guessing the
  average, and R² can go negative if a model does *worse* than that
  naive guess (which is exactly what happened before adding the trend
  feature -- see Section 3).

### Why Random Forest hyperparameters were chosen

- `n_estimators=300`: more trees generally reduce variance and stabilise
  predictions, with diminishing returns past a few hundred; 300 is a
  reasonable balance of accuracy vs training time on a dataset this size.
- `max_depth=14`: caps how deep each tree can grow, which limits
  overfitting to noise in individual hours.
- `min_samples_leaf=3`: requires at least 3 samples per leaf, another
  overfitting guard.
- `random_state=42`: fixes the random seed so results are reproducible.

## 5. The Flask backend (`app.py`)

Routes:

| Route | Method | Purpose |
|---|---|---|
| `/` | GET | Serves the dashboard HTML page. |
| `/api/dashboard-data` | GET | Returns all pre-aggregated chart series (daily trend, hourly/monthly/day-of-week profiles, actual-vs-predicted, summary stats) as one JSON payload. |
| `/api/metrics` | GET | Returns the model comparison table. |
| `/api/feature-importance` | GET | Returns Random Forest feature importances. |
| `/api/predict` | POST | Takes `{"date": "YYYY-MM-DD", "hour": 0-23}`, builds the same feature vector used in training, and returns a live prediction. |

**Why pre-aggregate instead of computing charts on every request?** The
heavy lifting (loading the Excel file, cleaning it, computing daily means,
etc.) happens once, offline, in `train_model.py`, and is saved to small
JSON files. The Flask app just reads those files into memory at startup
and serves them -- so every page load is fast, and the app doesn't need
pandas installed on a lightweight production server if you ever split
training from serving.

**Consistency between training and prediction:** `build_feature_vector()`
in `app.py` deliberately mirrors `add_calendar_features()` in
`preprocess.py` line-for-line for the fields it needs. This is called
out explicitly in the code comments because it's a real risk: if the two
ever drift apart (e.g. someone changes how `is_weekend` is computed in
one file but not the other), the model will silently make worse
predictions with no error thrown.

## 6. The frontend (`templates/`, `static/`)

Plain HTML + CSS + vanilla JavaScript (no build step, no framework) --
deliberately simple so it's easy to read and modify. Charts are rendered
with [Chart.js](https://www.chartjs.org/) loaded from a CDN. Fonts are
Space Grotesk (headings/numbers) and IBM Plex Sans (body text) from
Google Fonts. The palette is a warm charcoal-and-amber "grid" theme
(no blues) defined as CSS custom properties in `static/css/style.css`.

The dashboard has four sections:
1. **Stat cards** -- peak/average/minimum demand and model MAPE
2. **Daily trend** -- full two-year time series
3. **Recurring patterns** -- hourly, monthly, day-of-week averages, and feature importance
4. **Model performance** -- actual vs. predicted on the test month, plus the comparison table
5. **Try it yourself** -- pick any date/hour and get a live prediction from `/api/predict`

## 7. Running it locally

```bash
# 1. Clone and enter the project
git clone <your-repo-url>
cd power-demand-forecast

# 2. Create a virtual environment (recommended)
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate

# 3. Install dependencies
pip install -r requirements.txt

# 4. Train the model (generates everything in models/)
python src/train_model.py

# 5. Run the app
python app.py

# 6. Open the dashboard
# http://127.0.0.1:5000
```

Re-run `python src/train_model.py` any time to retrain with different
hyperparameters or a different feature set -- the app reads whatever is
currently in `models/`.

## 7.5 Hosting it so anyone can open it on their phone

The dashboard is a normal web page once it's deployed -- any phone with a
browser can open it, no app install needed. The Flask dev server used
above (`python app.py`) is fine for your own laptop, but it isn't meant
to be exposed to the internet, so a real deployment uses **gunicorn**
(a production-grade WSGI server, already in `requirements.txt`) instead.

### Option A -- Render (recommended: no credit card, free tier)

1. Push this project to a GitHub repository (see Section 9 below).
2. Go to [render.com](https://render.com) and sign up / log in with GitHub.
3. Click **New +** → **Web Service**, then pick your repository.
4. Render should detect `render.yaml` automatically and pre-fill:
   - **Build command:** `pip install -r requirements.txt && python src/train_model.py`
   - **Start command:** `gunicorn app:app --bind 0.0.0.0:$PORT`
   - **Plan:** Free
   (If it doesn't auto-detect, paste those two commands in manually.)
5. Click **Create Web Service**. The first deploy takes a few minutes
   (installing dependencies + training the model).
6. Render gives you a public URL like `https://gridwatch-power-demand.onrender.com`.
   Open that on your phone -- that's it.

**One thing to know about the free tier:** Render's free web services spin
down after ~15 minutes of no traffic. The next visit after that will take
20-30 seconds to "wake up" while it restarts -- normal behavior, not a bug.

### Option B -- PythonAnywhere (good if you'd rather not touch a CLI)

PythonAnywhere runs everything through a browser-based dashboard (upload
files, open a console, configure a "web app") without needing Git at all,
which makes it a good option if you want to avoid GitHub/CLI steps
entirely. Search their docs for "Flask" when you get to the web app setup
step, since the exact menu labels shift between their UI versions.

### Option C -- Railway

Similar flow to Render (connect a GitHub repo, it detects the `Procfile`
and deploys), but its free usage allowance is smaller, so it suits short
demos more than something you'll leave running indefinitely.

### A note on picking a platform

Free tiers on these platforms change fairly often (limits, whether a
credit card is required, etc.), so if something above doesn't match what
you see on the platform's site, trust the platform's current docs over
this README and search for "<platform name> Flask deploy" to confirm.

## 9. Ideas for extending this project

Good talking points if an interviewer asks "what would you do next?":

- **Add lag/rolling features** (demand 24h and 168h ago, 24h rolling mean)
  for a separate "next-hour forecast" mode, alongside the calendar-only
  "what-if" mode this dashboard already has.
- **Add weather data** (temperature is a huge driver of cooling/heating
  load) as an external feature.
- **Try gradient boosting** (XGBoost/LightGBM) or a seasonal time-series
  model (SARIMA, Prophet) and compare against the Random Forest baseline.
- **Quantify uncertainty** -- report a prediction interval (e.g. using
  the spread across the Random Forest's individual trees) instead of a
  single point estimate.
- **Swap the dev server for a production WSGI server** (gunicorn/uWSGI)
  behind nginx before deploying anywhere public.
